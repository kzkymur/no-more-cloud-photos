# NMCP Photos (mobile)

Automatically uploads the photos and videos on a phone to your own
no-more-cloud-photos server (`POST /media` of the Core API). Originals are sent
byte-for-byte: no re-encoding, no metadata stripping (HEIC stays HEIC, GPS EXIF
is kept).

- UI: React Native (Expo SDK 58), `App.tsx`.
- Upload core: local Expo module `modules/nmcp-uploader`, native Kotlin
  (`android/`) and Swift (`ios/`). Scanning, the "already uploaded" ledger,
  background scheduling and the HTTP upload all run natively so they keep working
  when the UI is not running.
- JS ↔ native contract: `modules/nmcp-uploader/src/NmcpUploader.types.ts`.

## Using the app

1. Install the APK (see "Android build" below). Android warns about installing
   from outside the Play Store; allow it for the app you downloaded it with.
2. Enter the server URL, e.g. `https://photos.<tailnet>.ts.net`. The app calls
   `GET /readyz`; you can only save the URL once that answers 2xx.
3. Allow access to **all** photos and videos. On Android also allow location
   access for photos. Without it Android removes GPS from every file the app
   reads, so the app **pauses uploading** (it never sends redacted bytes as an
   "original") and shows a button to grant it. If you pick "selected photos
   only" the app shows a warning and only uploads what you selected.
4. The dashboard shows total / uploaded / pending / failed, the file in
   progress, and the last error. "今すぐ同期" (sync now) runs immediately and
   ignores the Wi-Fi/charging conditions; "失敗を再試行" (retry failed) queues
   every failed item again.

The server has no authentication: it must only be reachable over your tailnet
(or LAN). The phone needs to be on the tailnet (Tailscale app connected) to
upload.

## How uploading works

Each library item is one upload (Live Photos on iOS are two: the still and the
paired video).

1. The file is read once to compute its SHA-256 and exact length.
2. It is sent as a single-part `multipart/form-data` body:

   ```
   --nmcp-<32 hex>\r\n
   Content-Disposition: form-data; name="file"; filename="<ascii fallback>"; filename*=UTF-8''<RFC 8187 percent-encoded name>\r\n
   Content-Type: <media type>\r\n
   \r\n
   <original bytes>\r\n
   --nmcp-<32 hex>--\r\n
   ```

3. `Idempotency-Key: nmcp1-<hex sha256("<platform>|<item id>|<content sha256 hex>|<filename>")>`
   (70 ASCII bytes; `<filename>` is the exact name written into the body).
   The key is stable for the same item, content and name. A retry after a lost
   response is therefore replayed by the server (`Idempotency-Replayed: true`)
   instead of creating a duplicate. The server's request hash covers the
   content and the filename, so the key covers both too. If a file is edited
   in place or renamed it gets a new key, and the server answers `201`
   (new bytes) or `409 duplicate_media` (same bytes). It never answers
   `409 idempotency_conflict`.

   The format is pinned by shared test vectors,
   `modules/nmcp-uploader/testdata/contract-vectors.json`. They are generated by
   the independent reference implementation `generate_vectors.py`; CI checks the
   committed file is current. They are asserted by:
   - Go: `internal/httpapi/mobile_client_contract_test.go`, which checks the
     handler accepts the exact bytes and the original arrives unaltered.
     `internal/upload/mobile_contract_integration_test.go` pins the
     201/replay/`duplicate_media`/`idempotency_conflict` response shapes against
     PostgreSQL.
   - Kotlin: `android/src/test/.../MultipartFormatTest.kt`
     (`:nmcp-uploader:testDebugUnitTest`).
   - Swift: XCTest package `tests/swift` (`swift test` on the macOS host; its
     sources are symlinks to the real `ios/` files). It also covers the
     multipart body writer, the response classifier, and the SQLite ledger
     (queue order, interrupts, v1→v2 migration, corrupt-file recovery).
4. How responses are handled:
   - `2xx`: uploaded.
   - `409 duplicate_media`: the same bytes are already on the server, so the
     item counts as uploaded.
   - `401`/`403`/`404`/`405` (wrong URL or a proxy in front of the API) and
     `429`/`502`/`503`/`504` (server busy or down): the run stops. The item stays
     pending without using up an attempt, and the error is shown on the dashboard.
   - `408`, other `5xx`, connection drop mid-transfer: transient failure,
     retried automatically on later runs (up to 10 attempts).
   - other `4xx` (e.g. `415 unsupported_media_type`, `422 invalid_media`,
     `413`): marked "rejected by server". It is not retried automatically,
     only by "retry failed".
   - server unreachable: the run stops and is retried with backoff. The item
     stays pending.
5. The local SQLite ledger records every item and its state. An uploaded item
   is never sent again unless the file changes.
6. Queue order: items that were interrupted mid-transfer fewer times go first,
   then pending before transient failures, then newest first. Uploads are not
   resumable and restart from byte 0. So a large video that keeps getting cut
   off moves behind the rest of the queue instead of blocking older items.

### Android

- Scan: MediaStore images + videos (`VOLUME_EXTERNAL`, `IS_PENDING = 0`).
  Bytes are always read through `MediaStore.setRequireOriginal()` on Android 10
  and later. Without `ACCESS_MEDIA_LOCATION`, uploading pauses.
- Scheduling (WorkManager):
  - `nmcp-trigger`: a MediaStore content-URI trigger that fires after new
    photos/videos appear.
  - `nmcp-periodic`: an hourly safety net that survives reboots.
  - `nmcp-auto`: the upload run, with the Wi-Fi-only / charging-only
    constraints.
  - `nmcp-manual`: "sync now", which only needs a network.

  Runs are serialized. A run shows a foreground notification (type `dataSync`)
  with progress. The app also syncs when it comes to the foreground.
- Limits:
  - Android 12+ usually refuses to start a foreground service from the
    background. A background run then gets about 10 minutes before WorkManager
    stops it, and the interrupted item is moved back in the queue. Very large
    videos on a slow uplink may only finish when "sync now" is used with the
    app open, because the foreground service is allowed then.
  - Android 15 caps `dataSync` foreground services at 6 hours per day.
- Permissions:
  - Android 13+: `READ_MEDIA_IMAGES`/`READ_MEDIA_VIDEO`.
  - Android 14+: `READ_MEDIA_VISUAL_USER_SELECTED`, which grants partial
    access and triggers the warning.
  - Android ≤ 12: `READ_EXTERNAL_STORAGE`.
  - Also requested: `ACCESS_MEDIA_LOCATION` and `POST_NOTIFICATIONS`.
- Cleartext HTTP is allowed, because tailnet traffic is already encrypted by
  WireGuard and `http://100.x.y.z:port` must work. Prefer `https://<host>.ts.net`.

### iOS

- Scan: PhotoKit. Only the original resources are sent: `.photo` (plus
  `.alternatePhoto` for RAW+JPEG), `.pairedVideo` for Live Photos, and
  `.video`. Edits (`fullSize*`) are never sent.
- Staging is a single copy: `PHAssetResourceManager.requestData` (with
  `isNetworkAccessAllowed`, so iCloud-only originals are downloaded) streams
  straight into the multipart body file while hashing. A body is used only
  when the request completed without error, so a partial download is never
  sent. The body is sent with a background `URLSession` upload task, which
  continues while the app is suspended.
- Interruptions are counted like on Android (`interrupts`, ledger v2). Each of
  these returns the item to the queue behind less-interrupted items, without
  using an attempt:
  - background time expiring while staging;
  - a kill or suspension mid-staging (counted before staging starts);
  - a cancelled or lost background transfer;
  - an unreachable server.

  Stop-run responses (401/403/404/405/429/502/503/504) also keep the item
  pending without using an attempt.
- iCloud download problems (offline, stalled for 120 s, storage full) fail the
  item for that run only, also without using an attempt. Five in a row stop the
  run with "Uploads will resume later".
- `BGTaskScheduler` refresh/processing tasks and a photo library change
  observer pick up new photos. The app also syncs when it comes to the
  foreground.
- Plain HTTP: ATS allows only local networking (`NSAllowsLocalNetworking`). Use
  `https://<host>.ts.net` (Tailscale HTTPS certificates).
- Background limits (by design of iOS):
  - iOS decides when `BGTaskScheduler` tasks run, and runs them less often for
    apps that are rarely opened.
  - When iOS wakes the app for background-session events, it gives about
    30 seconds to prepare the next item. A large or iCloud-only original that
    cannot be exported in that time waits until the next background task or
    the next time the app is opened. The chain also slows down because iOS
    delays relaunches for apps that keep starting background uploads.
  - Initial backup is fastest with the app open.
  - iCloud original downloads follow the Photos cellular setting, not the
    app's Wi-Fi-only option.
  - Hidden photos (`includeHiddenAssets = false`) are not backed up.
  - Live Photo still and video are uploaded as two separate media. The server
    does not pair them yet (follow-up issue), but both files keep the Apple
    content identifier, so the pairing can be rebuilt later.
- Workflow **Mobile iOS** (`.github/workflows/mobile-ios.yml`):
  - job `test` (PRs and `main`) runs:
    - the XCTest package;
    - an unsigned Release build for the simulator;
    - the simulator end-to-end test (`e2e/run_ios_simulator_e2e.sh` against
      `e2e/stub_core_api.py`). It imports GPS-tagged JPEG/HEIC into Photos and
      checks four things: originals arrive byte-identical with GPS, a lost
      response is replayed with the same key, an identical copy settles as
      `duplicate_media`, and nothing is re-sent after relaunch.
  - job `testflight` (`main` push / dispatch on `main`, environment
    `ios-release`) archives with automatic signing through an App Store
    Connect API key and uploads to TestFlight.
- Distribution: TestFlight. Customer setup: `docs/ios-testflight-setup.md`;
  on-device acceptance checklist: `docs/ios-acceptance.md`. The simulator E2E is
  currently non-blocking (iOS 26 simulators cannot be granted full Photos access
  without UI; follow-up #76).
  The bundle id comes from `NMCP_IOS_BUNDLE_ID` (`app.config.js`).

## Android build

GitHub Actions workflow **Mobile Android** (`.github/workflows/mobile-android.yml`):

- Job `check` (pull requests): contract-vector check, typecheck, Kotlin unit
  tests, and a release build signed with the throwaway debug key. It uses no
  secrets and publishes nothing.
- Job `release` (push to `main` touching `mobile/`, or manual dispatch on
  `main`): builds the APK signed with the permanent release key, verifies the
  certificate, and publishes the artifact `nmcp-photos-android` (90 days). It
  runs in the protected environment `android-release` (required reviewers,
  `main` only), which holds the secrets:

| Secret | Content |
|---|---|
| `NMCP_ANDROID_KEYSTORE_BASE64` | base64 of the PKCS12 release keystore |
| `NMCP_ANDROID_KEYSTORE_PASSWORD` | store password (also the key password) |
| `NMCP_ANDROID_KEY_ALIAS` | key alias |

Release certificate SHA-256:
`11:9E:F3:C6:B5:ED:68:92:2B:E2:9F:EE:BF:F4:70:1C:BD:88:05:04:BA:C7:3D:F3:47:B9:85:48:C4:24:CD:90`
(the workflow verifies it). An update signed with any other key cannot be
installed over an existing install, so the key must never change.

Bump `expo.version` and `expo.android.versionCode` in `app.json` for each
release you hand out.

Local development (needs JDK 17 and the Android SDK):

```sh
cd mobile
npm ci
npx expo prebuild --platform android --clean   # android/ is generated, never edited
cd android && ./gradlew assembleRelease
```

`android/` and `ios/` are generated by `expo prebuild` (Continuous Native
Generation) and are git-ignored. Native configuration lives in `app.json`,
`plugins/withReleaseSigning.js`, and the module's own `AndroidManifest.xml` /
podspec.
