Core Worker仕様骨子

短いレビュー版です。
確定提案要確認を分け、変換実装前に必要な境界だけを示します。

Core WorkerはGo（os/exec）、管理CLIはGo（flag）で作ります。全体構成はCore技術仕様を参照。

1. 入出力

  • 確定原本は無改変で保持。初期入力はJPEG / PNG / GIF / HEIC / RAW / WebP / BMP、動画はMP4 / MOVを対象とし、将来は消費者向け形式全般を目標にします。
  • 確定RAWは形式群の総称、MP4 / MOVはcontainerです。列挙した全codec・全RAW派生形式の読込成功を一律には保証せず、内容検出MIMEとprocessor能力で判定します。
  • 確定静止画standardはAVIF。cropせず縦横比を保って長辺を最大1920pxへ縮小し、小さい原本は拡大しません。
  • 確定thumbnailはcropせず縦横比を保って長辺を最大640pxへ縮小し、小さい原本は拡大しません。
  • 確定動画standardはMP4 container + AV1 video、音声があればAAC。cropせず縦横比を保って長辺を最大1920pxへ縮小し、小さい原本は拡大しません。encoder要件に合わせ、奇数寸法は縮小側の偶数へ丸めます。
  • 要確認AVIF／AV1の品質値、bit depth、metadata保持範囲は実測とViewer検証後に調整します。

2. 静止画・動画・animation

  • 確定向き・rotationは画素へ適用して正規化します。静止画SDRはsRGB、動画SDRはBT.709へ統一し、HDR入力はSDRへtone mapします。動画へsRGB metadataを機械的に適用しません。原本は無改変です。
  • 確定動画thumbnailは先頭frameをAVIF静止画にし、長辺最大640px、縦横比維持、cropなし、非拡大を適用します。
  • 確定GIF / WebP animationのstandardは動きを保持し、thumbnailは先頭frameの静止画にします。
  • 技術初期値animationのstandard出力はanimated WebPを採用し、alpha・frame timing・loopを保持します。これはユーザー指定の形式ではなく初期実装案であり、decoder / encoderの対応を実装前に検証します。

3. Profile ↔ Processor契約

  • 確定active profileには、そのinput_mime_typesとparameters schema/versionを実行できるprocessorが必要です。Workerはjob targetが固定したprofile版を実行します。
  • 確定profile追加が常に1対1の新processor実装を意味するわけではありません。既存processorを設定違いの複数profileで再利用できます。新しい変換能力には対応processor追加が必要です。
  • 提案profileをactiveにする前に、processor名・対応schema version・入力MIME・出力recipeの互換性を検証し、対応実装がなければactive化を拒否します。

4. 自動生成と受付境界

  • 確定POST /media時、Coreが内容検出MIMEに一致するactive profilesを選び、1 jobとprofileごとのtargetsを作成。0件なら原本だけ保存しjobは作りません。
  • 確定profile新版は新規uploadから利用。既存Mediaは旧currentを表示し、必要な再生成は管理batchで行います。profile activationだけで一斉再生成しません。
  • 確定同一sha256は重複として新規登録しません。提案Coreが409と既存Media IDを返します。通信再送の冪等性もCore API側の責務です。
  • 確定撮影日時に既知のoffsetがあればそれを優先し、不明な場合だけsystem_config.default_timezoneで補完します。初期値はIANA名Asia/Tokyoで、設定時にIANA timezone名として検証します。
  • 確定既定timezoneの変更は既存taken_atへ遡及しません。原EXIFはoriginals.exif_jsonへ保ち、補完根拠と利用timezoneをMediaに記録します。

重複判定・撮影日時補完・job作成はCore受付責務であり、Worker単体の変換仕様ではありません。

5. 低資源での実行案

  • 提案CPU 2個分・メモリ4GiBをシステム全体の初期目安とし、Workerは並列1と変換toolのthread上限から始めます。各serviceへ同じ上限を重複配賦しません。
  • 要確認品質・処理時間・peak memoryは未検証です。AVIF／AV1と巨大RAWを代表sampleで実測して調整し、AV1が遅くてもH.264へ自動fallbackしません。

6. 次に確認する項目

  • AVIF／AV1品質、bit depth、metadata保持範囲。
  • animated WebPのdecoder / encoder対応、Viewer対象端末での表示品質。
  • AV1 software encodeの処理時間と資源上限。
